# future_work_for_poor_developer.md — 적은 Claude 자원으로 실사용 편의성 높이기

기준 시점: 2026-08-15. `future_work.md`는 "상용 GUI 앱과 비교하면 뭐가 부족한가"를 기준으로 썼는데,
이 앱은 애초에 상용 제품이 아니라 **개발자 한 명(사용자 본인)이 자기가 쓸 도구를 직접 만드는
개인용 프로그램**이다. 다크모드, 온보딩, 위젯 라이브러리 확장, 반응형 레이아웃, 접근성/다국어처럼
"다른 사용자"를 전제로 한 항목은 여기선 의미가 없다. 대신 **"주어진 Claude 자원(대화 횟수/시간)이
한정된 상태에서, 그 자원을 어디에 써야 실사용 편의성이 가장 많이 오르는가"**를 기준으로 다시 짰다.

## 이 세션이 보여준 진짜 병목

이번 대화 세션 전체를 돌아보면, 시간이 가장 많이 든 건 새 기능 추가가 아니라 **"여백을 좌우와 같게",
"간격을 모두 동일하게" 같은 요청 하나를 처리하려고 매번 임시 헤드리스 스크립트를 새로 짜서 픽셀을
재고, `builder_state.json`을 손으로 고치고, 앱을 껐다 켜서 확인하는 반복 사이클**이었다. 이 사이클
자체가 없어지거나 짧아지면, 앞으로 같은 종류의 요청을 처리할 때 Claude 자원이 지금의 몇 분의 1만
들게 된다 - 즉 **"기능 추가"보다 "다음 요청을 더 싸게 만드는 도구"가 더 높은 레버리지**를 가진다.

## 1. 레이아웃 검사 스크립트 상비

**문제**: 이번 세션에서 "여백이 같은지", "간격이 동일한지" 확인할 때마다 매번 새 스크래치 스크립트를
`QT_QPA_PLATFORM=offscreen`으로 짜서 특정 탭/위젯의 geometry를 찍었다. 스크립트 자체는 5~10줄
안팎으로 짧지만, **매번 새로 작성하고 대상 탭 이름을 바꾸고 import 경로를 맞추는 데 드는 왕복
시간**이 쌓여서 전체 세션의 상당 부분을 차지했다.

**해결**: 저장소에 `tools/inspect_layout.py` 하나를 만들어서, 인자로 탭 이름(또는 전체)을 받아
`CanvasWindow`를 헤드리스로 띄우고 그 탭의 모든 위젯의 x/y/width/height와, **인접한 두 위젯 사이의
여백(오른쪽 끝-왼쪽 시작 등)까지 자동 계산**해서 표로 찍어준다. 예:

```
python tools/inspect_layout.py gvf
gvfpanel_1     x=20  y=20  w=379 h=250  (좌측여백=20)
fpgaacq_1      x=421 y=20  w=379 h=250  (gvfpanel_1과의 간격=22, 우측여백=20)
fpgaload_1     x=8   y=283 w=804 h=181  (좌측여백=8, 상단간격=13, 하단여백=8)
```

이러면 "여백을 같게 해달라"는 요청이 왔을 때 Claude가 스크립트 하나만 실행해서 바로 현재 상태를
파악하고, 목표값을 계산해서 바로 JSON을 고치면 된다 - 지금처럼 매번 스크립트를 새로 작성하는
단계가 통째로 사라진다.

**예상 소요**: 30분 이내. 이미 이번 세션에서 반복 작성했던 로직을 한 번만 정리하면 됨.

## 2. 여백/정렬 관계를 JSON에 선언식으로 기술

**문제**: "A의 왼쪽 여백을 B의 왼쪽 여백과 같게" 같은 요청은 지금 **한 번 맞춰놔도 그 뒤에 A나 B의
폭/위치가 바뀌면 다시 깨진다** - 실제로 이번 세션에서 gvf 탭 세 사각형 크기를 여러 번 조정할 때마다
"여백을 다시 맞춰달라"는 요청이 반복해서 왔다.

**해결**: `builder_state.json`의 위젯 항목에 선택적으로 `anchor` 필드를 추가한다 (예:
`"anchor": {{"left": "gvfpanel_1.left", "right": "fpgaacq_1.right"}}`). 저장 시점에 이 필드가 있는
위젯은 캔버스가 다른 위젯의 최종 좌표를 기준으로 자동 계산해서 배치한다. 처음엔 저장/복원 로직에만
반영하고(드래그 UI 연동은 생략), Claude가 JSON을 손으로 고칠 때 "이 위젯은 항상 저 위젯 기준으로
따라간다"고 한 번만 선언해두면 이후 크기 변경 요청에 여백 재계산이 자동으로 따라온다.

**예상 소요**: 1~2시간. `_restore_from_state`에 앵커 해석 단계 하나만 추가하면 됨 - UI 편집기 없이
JSON 필드만으로 동작.

## 3. 자동 저장

**문제**: `_save_state`가 정상 종료 시에만 실행돼서, 강제 종료·크래시가 나면 마지막 저장 이후 모든
작업이 사라진다. 이번 세션에서도 앱을 수십 번 껐다 켰는데, 그 중 하나라도 비정상 종료였으면 직전
작업이 통째로 날아갔을 것.

**해결**: `QTimer`로 1~2분마다 `builder_state.autosave.json`에 별도 저장, 시작 시 비정상 종료 흔적이
있으면 복구 여부만 물음.

**예상 소요**: 1~2시간.

## 4. 방향키 미세 이동

**문제**: 마우스 드래그로는 1px 단위 배치가 불가능해서, 정밀 배치가 필요할 때마다
`builder_state.json`을 직접 편집해야 했다(이번 세션 내내 반복).

**해결**: `CanvasPage.keyPressEvent`에 화살표 키 처리 추가(1px, Shift+화살표 10px).

**예상 소요**: 30분~1시간. 이 목록에서 시간 대비 효과가 가장 좋은 항목 중 하나.

## 5. 겹침 순서(z-order) 제어

**문제**: 위젯이 겹치면 나중에 배치한 게 항상 위, 바꿀 방법이 없다.

**해결**: 우클릭 메뉴에 "맨 앞으로"/"맨 뒤로" 추가.

**예상 소요**: 1시간.

## 6. 위젯 X/Y/W/H 숫자 직접 입력

**문제**: `future_work.md`의 "속성 패널"(5~8시간)은 개인용 도구엔 과함 - 색상/폰트까지 통합 패널을
만들 필요는 없다. 하지만 **정확한 좌표를 숫자로 입력하는 기능 하나만큼은** 이번 세션에서 극심하게
아쉬웠다(`builder_state.json`을 직접 열어 고친 게 수십 번).

**해결**: 우클릭 메뉴에 "위치/크기..." 항목 하나 추가 - X/Y/W/H 숫자 입력 4칸짜리 작은 다이얼로그
(기존 "이름 변경" 다이얼로그와 같은 패턴). 속성 패널 전체를 만들 필요 없이 이 하나만 있어도
"픽셀 단위로 정확히 옮겨달라"는 요청의 대부분을 대화 없이 사용자가 직접 처리할 수 있게 됨.

**예상 소요**: 2~3시간.

## 7. 정렬 가이드 + 스냅(단순 버전)

**문제**: `future_work.md`에서 가장 효과가 크다고 봤던 항목인데, 완전한 Figma식 스냅(가이드선+균등
배분 도구)은 3~4일이 걸린다. 개인용으로는 그렇게까지 정교할 필요 없다.

**해결**: 축소판으로 시작 - 드래그 중인 위젯이 다른 위젯과 **왼쪽/오른쪽/위/아래 가장자리가 ±3px
이내로 맞으면 그 값으로 딱 붙기만** 하고, 가이드선이나 중앙 정렬, 균등 배분은 생략. 이것만으로도
"여백을 같게" 요청의 상당수가 대화 없이 마우스로 끝난다.

**예상 소요**: 3~4시간(가이드선/균등배분 없는 버전 기준. `future_work.md`의 전체 버전 4~6시간보다
저렴).

## 8. 실행취소(Undo) - 딱 삭제만

**문제**: `future_work.md`의 전체 Undo/Redo(이동/리사이즈/색상/폰트 전부 포함, 4~7시간)는 개인용
도구엔 과하다. 실제로 뼈아픈 건 **위젯을 실수로 삭제했을 때 연결된 "동작 설정" 코드까지 통째로
사라지는 것** 하나뿐이다.

**해결**: 전체 Command 패턴 대신, 삭제 전용 1단계 Undo만 구현 - `_delete_selected_widgets` 호출 시
지워지는 위젯들의 전체 데이터를 임시 변수 하나에 저장해두고, Ctrl+Z를 누르면 그 하나만 되돌림(다음
삭제가 일어나면 이전 것은 잊어버려도 됨 - 완전한 스택 불필요).

**예상 소요**: 1~2시간. 전체 Undo/Redo의 1/3 비용으로 가장 아픈 케이스만 해결.

## 완전히 제외한 것과 이유

`future_work.md`에 있던 항목 중 이 문서에서 뺀 것들과 이유:

- **다크 모드** — 순전히 취향 문제. 사용자 본인이 원하지 않는 한 우선순위 없음.
- **앱 아이콘** — 이미 완료(2026-08-15 커밋 `0bdaf93`).
- **캔버스+팔레트 단일 창 통합** — 사용성 개선은 맞지만, 지금 방식(별도 창 두 개)도 이미 손에
  익어서 급하지 않음.
- **위젯 라이브러리 확장(체크박스/슬라이더/테이블 등)** — 지금 쓰는 5개 탭(git/wiki/gvf/윈도우현황/
  alarm) 어디에도 이런 위젯이 필요한 구체적 케이스가 없음. 실제로 필요해지는 순간 그때 추가하는 게
  더 쌈.
- **반응형(레이아웃 기반) 내보내기** — `future_work.md`에서 가장 비쌌던 항목(3~5일)인데, 애초에
  CLAUDE.md가 "창 크기를 바꾸지 않는다"는 원칙을 못박아둔 개인용 고정 대시보드라서 반응형 자체가
  필요 없음.
- **설정(Preferences) 창 / 첫 실행 온보딩 / 비모달 토스트** — 전부 "다른 사용자"를 전제로 한 편의
  기능. 사용자 본인은 이미 이 앱의 동작 방식을 다 알고 있어서 얻는 게 거의 없음.
- **접근성/다국어** — 원래 문서에서도 제외됐던 항목, 여기서도 동일.

## 권장 순서

1. **1번(레이아웃 검사 스크립트)을 가장 먼저** - 이후 모든 레이아웃 관련 요청 자체의 비용을
   낮춰서, 뒤에 나올 항목들(그리고 앞으로의 모든 요청)이 다 더 싸게 끝난다.
2. **3, 4, 5번(자동저장/방향키/z-order)** - 셋 다 합쳐 반나절 이내, 즉시 체감되는 안전망+편의.
3. **6번(X/Y/W/H 숫자 입력)** - `builder_state.json`을 손으로 고치던 습관 자체를 없앰.
4. **2번(앵커 선언)과 7번(단순 스냅)** - 이번 세션에서 제일 많이 겪은 "여백 재조정" 요청을 근본적으로
   줄임. 여유 있을 때 진행.
5. **8번(삭제만 Undo)** - 안전망 성격이라 언제 넣어도 되지만, 시간 남으면 마지막으로.
