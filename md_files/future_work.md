# future_work.md — 상용 GUI 앱 대비 격차 분석 및 향후 작업

기준 시점: 2026-08-15. `canvas_window.py`/`palette_window.py`/`theme.py`/`tab_bar.py`/
`behavior_dialog.py` 등 빌더 본체 코드를 직접 읽고, Figma·PowerPoint·Qt Designer·VS Code 같은
실제 상용 GUI 툴과 비교해 **GUI/UX 관점에서만** 격차를 정리했다. 기능(자연어 동작 생성, standalone
내보내기 등) 자체의 부족함이 아니라, "화면을 만들고 다듬는 경험"이 상용 툴 대비 얼마나 불편한지에
집중했다.

**시간 추정 기준**: 이 프로젝트는 1인 개발자가 처음부터 설계하는 전통적인 방식이 아니라 Claude가
직접 구현하는 방식으로 진행된다. 이 세션에서 실제로 "여백을 좌우와 같게 맞춰" 같은 요청 하나를
처리하는 데 (실측·검증 포함) 10~30분 정도 걸렸던 실제 속도를 기준으로 잡았다 - 그래서 아래 추정은
전부 **일(day) 단위가 아니라 시간(hour) 단위**다. 유일한 예외는 13번(반응형 내보내기)로, 이건
전체 아키텍처를 다시 짜야 해서 실제로도 여러 세션에 걸친 작업이 된다.

## P0 — 일상 사용에 직접 영향

### 1. 자동 저장(크래시 복구)

**상용 앱 대비**: Word/Figma 등은 수 분 간격으로 백그라운드 자동 저장하고, 비정상 종료 후 재시작하면
복구 여부를 묻는다.

**현재 상태**: `_save_state`는 앱을 정상 종료(`closeEvent`)하거나 "틀 저장" 버튼을 눌렀을 때만
실행된다. 강제 종료(작업관리자 종료, 정전, 크래시)가 나면 마지막 수동 저장 이후 모든 작업이 사라진다.

**구현 방향**: `QTimer`로 1~2분마다 `_save_state`를 별도의 `builder_state.autosave.json`에 기록.
`main.py` 시작 시 이 파일이 정상 종료로 지워지지 않고 남아있으면(=비정상 종료 흔적) "복구할까요?"
확인창을 띄움.

**예상 소요**: 1~2시간. 로직 자체가 단순해서 이 목록 전체에서 가장 빠르게 끝낼 수 있는 항목 중
하나.

### 2. 방향키 미세 이동

**상용 앱 대비**: 모든 디자인 툴이 화살표 키로 1px, Shift+화살표로 10px 이동을 지원한다.

**현재 상태**: 선택된 위젯을 키보드로 옮길 방법이 전혀 없다(`keyPressEvent`는 Delete/Copy/Paste만
처리). 마우스 드래그만으로는 1px 단위 미세 조정이 사실상 불가능하다 - 이번 세션에서 정확한 픽셀
배치가 필요할 때마다 `builder_state.json`을 직접 편집해야 했던 것도 이 부재가 한 원인.

**구현 방향**: `CanvasPage.keyPressEvent`에 화살표 키 분기 추가, 선택된 모든 위젯을 1px(Shift 시
10px) 이동.

**예상 소요**: 30분~1시간. 이 목록에서 가장 적은 코드로 가장 즉각적인 효과를 내는 항목.

### 3. 겹침 순서(z-order) 제어

**상용 앱 대비**: 위젯을 겹쳐 놓을 때 "맨 앞으로/맨 뒤로" 보내는 기능은 기본이다.

**현재 상태**: 위젯이 놓인 순서(드롭한 순서)대로만 겹치고 바꿀 방법이 없다. 뒤에 깔린 위젯을 나중에
앞으로 꺼낼 수 없다.

**구현 방향**: 우클릭 메뉴에 "맨 앞으로"/"맨 뒤로" 추가, `widget.raise_()`/`widget.lower()` 호출.
저장 시 위젯 리스트의 순서 자체가 z-order를 의미하므로 별도 필드 불필요.

**예상 소요**: 1시간.

### 4. 실행취소/다시실행 (Undo/Redo)

**상용 앱 대비**: PowerPoint·Figma·Qt Designer 등 위젯을 배치/편집하는 툴은 예외 없이 Ctrl+Z를
지원한다. 오배치·실수 삭제가 필연적으로 일어나는 작업 특성상 사실상 필수 기능으로 취급된다.

**현재 상태**: `CanvasPage`에 이동/크기조절/삭제/색상변경/폰트변경/이름변경/붙여넣기 등 모든 편집이
즉시 적용되고 되돌릴 방법이 없다. 위젯을 실수로 삭제하면(Delete 키에 확인창도 없음) 여기 연결된
"동작 설정" 코드까지 통째로 사라지고 복구 불가능하다.

**구현 방향**: Command 패턴으로 각 편집 동작(이동/리사이즈/삭제/붙여넣기/색상/폰트/이름/라디오
옵션 추가삭제)을 "실행"과 "되돌리기" 쌍으로 감싸고, `CanvasPage`마다 undo/redo 스택을 둔다. 위젯이
`deleteLater()`로 실제 파괴되는 삭제 케이스가 가장 까다로움 - 되돌릴 때 같은 `entries` 구조로
재생성해야 함(이미 `restore_widget` 경로가 있어 재사용 가능).

**예상 소요**: 4~7시간. 이동/리사이즈처럼 연속 드래그 동작을 하나의 undo 단위로 묶는 처리(마우스
릴리즈 시점에만 스택에 push)가 시간이 가장 많이 드는 부분.

### 5. 정렬 가이드 + 스냅

**상용 앱 대비**: Figma/PowerPoint는 위젯을 드래그하면 다른 위젯과 가장자리·중앙이 맞을 때 분홍색
가이드선이 뜨고 자동으로 달라붙는다(snap). 여백을 균등하게 만드는 "distribute evenly" 도구도 있다.

**현재 상태**: 순수 픽셀 드래그뿐이다. **이번 세션 전체가 이 기능의 부재를 보여주는 사례** - "여백을
좌우와 같게", "간격을 모두 동일하게" 같은 요청을 처리할 때마다 헤드리스 스크립트로 실제 렌더링
좌표를 일일이 측정하고 손으로 픽셀 값을 계산해야 했다. 상용 툴이었다면 스냅 가이드가 뜨는 순간
사용자가 마우스로 끌어다 놓기만 하면 끝날 일이었다.

**구현 방향**: 드래그/리사이즈 중(`_apply_resize`/드래그 핸들러) 현재 위젯의 상하좌우 가장자리·중앙선을
같은 탭의 다른 위젯들과 비교해 임계값(예: 4px) 이내면 그 값으로 스냅하고, 일치한 축에 안내선을
그린다(`paintEvent`에 임시 가이드 라인 추가).

**예상 소요**: 4~6시간. "균등 간격 배분" 도구까지 포함하면 +1~2시간.

### 6. 속성 패널 (Property Inspector)

**상용 앱 대비**: Qt Designer/Figma 등은 위젯을 선택하면 옆에 고정된 패널에 X/Y/W/H, 색상, 폰트,
텍스트 등 모든 속성이 한 번에 보이고 그 자리에서 바로 편집된다.

**현재 상태**: 속성 편집이 전부 우클릭 메뉴 → 각각 별도의 모달 다이얼로그(`QColorDialog`,
`QFontDialog`, 직접 만든 이름변경 `QDialog`)로 흩어져 있다. 지금 값이 뭔지 보려면 다이얼로그를 일단
열어야 하고, 정확한 X/Y/폭/높이를 숫자로 입력할 방법 자체가 없다(전부 마우스 드래그로만 가능 - 이번
세션에서 정확한 픽셀 배치가 필요할 때마다 `builder_state.json`을 직접 편집해야 했던 이유이기도 함).

**구현 방향**: `CanvasWindow`에 `QDockWidget` 속성 패널을 추가. 선택된 위젯(단일 선택 시)의
X/Y/W/H를 `QSpinBox` 4개로 양방향 바인딩(패널 수정 시 위젯 이동, 위젯 드래그 시 패널 갱신), 색상은
스와치+피커, 폰트는 콤보박스, 텍스트는 인라인 편집. 기존 우클릭 메뉴는 패널이 없는 상태를 위해 당분간
유지 가능.

**예상 소요**: 5~8시간. 양방향 바인딩(위젯→패널, 패널→위젯) 및 다중 선택 시 표시 방식 결정에 시간이
가장 많이 듦 - 이 목록에서 단일 항목으로는 가장 오래 걸림.

## P1 — 품질/완성도

### 7. 다크 모드

**상용 앱 대비**: Windows 자체가 시스템 다크 모드를 제공한 지 오래고, 대부분의 최신 데스크톱 앱은
OS 설정을 따라가거나 최소한 토글을 제공한다.

**현재 상태**: `theme.py`가 밝은 팔레트 하나만 하드코딩되어 있고 전환 수단이 없다. standalone으로
내보낸 앱도 항상 이 밝은 테마 그대로다.

**구현 방향**: `theme.py`를 `LIGHT_STYLESHEET`/`DARK_STYLESHEET` 두 개로 분리(대부분 색상 변수
치환), 팔레트 창에 토글 버튼 추가, 선택값을 `appData/`에 저장. `exporter.py`가 내보내는 소스에도
동일하게 반영.

**예상 소요**: 3~5시간. QSS 자체는 색상값 치환이라 기계적이지만, `git_widget.py`/`gvf_widget.py` 등
자체 인라인 스타일시트를 쓰는 합성 위젯(시계 배경색 등)들도 전부 다크 모드 대응이 필요해서 손이 많이
감.

### 8. 캔버스+팔레트 단일 창 통합

**상용 앱 대비**: Qt Designer, Figma, PowerPoint 등은 도구 패널이 메인 창에 도킹되어 있어 잃어버릴
수 없고 창 하나로 관리된다.

**현재 상태**: 캔버스(`CanvasWindow`)와 팔레트(`PaletteWindow`)가 완전히 분리된 OS 최상위 창
두 개다. 알트탭에 두 개가 따로 뜨고, 하나가 다른 하나 뒤에 가려지기 쉽고, 독립적으로 움직여서 서로
어디 있는지 놓치기 쉽다.

**구현 방향**: `CanvasWindow`를 `QMainWindow`로 유지하고 팔레트 내용을 `QDockWidget`으로 왼쪽에
도킹. `PaletteWindow`의 위젯 생성 로직 자체는 거의 그대로 재사용 가능.

**예상 소요**: 2~3시간.

### 9. 앱 아이콘 + 고해상도(DPI) 대응

**상용 앱 대비**: 모든 상용 앱은 작업표시줄/알트탭에서 구분되는 고유 아이콘이 있고, 고해상도
모니터에서 흐릿하게 안 보이도록 DPI 인식을 명시한다.

**현재 상태**: `CanvasWindow`/`PaletteWindow` 모두 `setWindowIcon` 호출이 없어 Qt 기본 아이콘 그대로
뜬다. 이번 세션 중 스크린샷 검증을 여러 번 시도하면서 이 머신이 250% DPI 스케일링을 쓰는데 앱이 이를
어떻게 다루는지 직접 확인된 바는 없음 - `QT_ENABLE_HIGHDPI_SCALING` 등 명시적 선언이 코드에 없어
Qt 기본 동작에 의존 중.

**구현 방향**: 아이콘 파일(.ico) 하나 만들어서 `main.py`에서 `QApplication.setWindowIcon` +
PyInstaller 빌드 시 `--icon` 옵션 추가. DPI는 `main.py` 최상단에 `QApplication` 생성 전
`Qt.HighDpiScaleFactorRoundingPolicy` 설정을 명시적으로 추가.

**예상 소요**: 코드 변경 자체는 1~2시간. 다만 실제로 보기 좋은 아이콘을 디자인하는 작업은 별도(이
문서의 시간 추정 범위 밖).

### 10. 삭제 확인/실행취소 일관성

**상용 앱 대비**: 탭 삭제는 확인창이 뜨는데 위젯 삭제는 안 뜬다 - 파괴력이 비슷한 두 동작의 안전장치
수준이 다르다. Gmail류 앱은 확인창 대신 "실행취소" 토스트를 잠깐 보여주는 방식을 쓴다.

**현재 상태**: `CanvasPage._delete_selected_widgets`는 확인 없이 즉시 삭제.

**구현 방향**: #4(Undo/Redo)이 구현되어 있다면 별도 확인창 없이 삭제 후 토스트로 "실행취소" 링크만
띄우는 것으로 충분(상용 앱 패턴). Undo 없이 이 항목만 단독으로 한다면 탭 삭제와 동일한
`QMessageBox.question` 확인창 추가.

**예상 소요**: Undo 있으면 30분(토스트 연동), 없으면 확인창만 1~2시간(다중 선택 삭제 시 문구 처리
포함).

## P2 — 기능 확장

### 11. 비모달 알림(토스트)

**상용 앱 대비**: "저장했습니다", "복사됨" 같은 단순 확인은 상용 앱 대부분 화면 구석에 잠깐
떴다 사라지는 토스트로 처리하고, 사용자의 다음 동작을 막지 않는다.

**현재 상태**: git 위젯 안내부터 "틀 저장 완료", "연결됨"까지 전부 `QMessageBox.information`
모달이라 매번 "확인"을 눌러야 다음 작업으로 넘어갈 수 있다. 반면 파괴적 동작(git clone,
process 종료, 파일 삭제)의 확인창도 똑같은 모달이라 시각적으로 구분이 안 됨.

**구현 방향**: 우측 하단에 잠깐 떴다 사라지는 작은 `QWidget` 토스트 컴포넌트를 만들어서, **정보성
알림만** 여기로 옮기고 파괴적 동작의 확인/경고는 기존 모달을 유지(구분이 오히려 더 명확해짐).

**예상 소요**: 3~4시간. 토스트 컴포넌트 자체는 1시간, 기존 `QMessageBox.information` 호출
15~20곳을 분류해서 교체하는 데 2~3시간.

### 12. 위젯 라이브러리 확장

**상용 앱 대비**: 체크박스, 슬라이더, 리스트/테이블, 이미지, 프로그레스 바, 메뉴바 등은 어떤 GUI
툴킷에도 기본 포함되는 위젯이다.

**현재 상태**: 팔레트에 드롭박스/버튼/텍스트박스/URL입력창/디렉토리입력창/라디오버튼/가로세로선
7종뿐이다. 체크박스조차 없어서(라디오 버튼만 있음) "독립적으로 켜고 끌 수 있는 옵션"을 표현할 수
없다.

**구현 방향**: 기존 `WIDGET_FACTORIES`/`LINE_DEFAULT_SIZE` 패턴이 이미 확장하기 쉽게 설계되어 있어,
새 위젯 하나당: 1) 캔버스 factory 함수, 2) 팔레트에 드래그 가능한 프리뷰, 3) `exporter.py`에 코드
생성 분기, 4) `code_binder.py`에 자연어 동작 바인딩(필요 시) 정도만 추가하면 됨.

**예상 소요**: 위젯 종류당 1~4시간(체크박스처럼 단순한 것은 1시간, 테이블/리스트처럼 데이터 바인딩이
필요한 것은 4시간 이상). 체크박스+슬라이더+프로그레스바 3종 세트면 약 4~6시간.

### 13. 설정(Preferences) 창

**상용 앱 대비**: 기본 폰트, 자동저장 주기, 기본 위젯 색상 같은 걸 앱 안에서 바꿀 수 있다.

**현재 상태**: 이런 값들이 전부 코드 상수(`LINE_DEFAULT_SIZE`, 각 파일의 매직넘버)이거나 JSON을
직접 고쳐야 바뀐다. 이번 세션에서도 색상·크기 조정은 전부 코드 수정을 거쳐야 했다.

**구현 방향**: `appData/settings.json` + 이를 편집하는 `QDialog` 하나 추가. 초반엔 자동저장 주기,
기본 배경색, 기본 폰트 정도만 노출해도 충분.

**예상 소요**: 2~3시간.

### 14. 첫 실행 온보딩/예제 갤러리

**상용 앱 대비**: 대부분의 툴이 처음 실행 시 빈 화면 대신 튜토리얼이나 샘플 프로젝트를 보여준다.

**현재 상태**: `CLAUDE.md`에 이미 "검토 대상"으로 명시된 알려진 격차다 - 지금은
`builder_state.json`이 없으면 그냥 빈 탭 하나로 시작하고, 있으면 사용자의 실사용 데이터(git/wiki/gvf
등)가 그대로 뜬다. 신규 사용자를 위해 큐레이션된 예제가 없다.

**구현 방향**: `builder_state.json`이 아예 없는 최초 실행 시에만 위젯 1~2개 + 자연어로 만든 동작
하나짜리 최소 예제 탭을 자동 생성. `executable_py/2026_07_26/app.py`가 이미 예시로 존재하므로 그
구성을 참고해 재현하면 됨.

**예상 소요**: 2~3시간.

### 15. 반응형(레이아웃 기반) 내보내기

**상용 앱 대비**: 상용 앱은 창 크기를 조절하면 내용물이 그에 맞게 재배치된다(레이아웃 매니저 기반).

**현재 상태**: 캔버스가 절대좌표 자유 배치 모델이고, `exporter.py`가 만드는 코드도 전부
`widget.move(x, y)` / `widget.resize(w, h)`로 고정 좌표를 굽는다. **CLAUDE.md 자체가 "빌더 창 크기를
바꾸지 않는다"는 원칙을 못박고 있는 것도 이 절대좌표 설계의 직접적인 결과** - 창 크기를 바꾸면 위젯이
하나도 안 따라 움직이기 때문이다. 내보낸 standalone 앱도 마찬가지라 사용자가 창을 늘려도 위젯들이
왼쪽 위에 고정된 채 나머지 공간은 빈다.

**구현 방향**: 근본적인 아키텍처 변경. 캔버스 위젯마다 "고정 크기" 대 "늘어남" 앵커 속성을 추가하고,
`exporter.py`가 절대좌표 대신 `QGridLayout`/`QVBoxLayout`+`stretch factor` 조합으로 코드를 생성하도록
전면 재작성해야 한다. 자유 배치 편집 경험(지금의 최대 장점)과 반응형 출력을 동시에 만족시키려면, 편집은
지금처럼 자유 배치로 하되 저장 시점에 "가장 가까운 그리드 셀"로 스냅해서 내보내는 하이브리드 접근이
현실적.

**예상 소요**: 3~5일. **이 목록에서 유일하게 시간이 아니라 일 단위인 항목** - 기존 위젯(git/gvf/alarm/
windowstatus 등 합성 위젯 포함) 전부를 다시 검증해야 해서, 아무리 빠르게 구현해도 여러 세션에 걸친
작업이 됨. 착수 전 "자유배치 편집 경험을 유지할지"에 대한 제품 결정이 먼저 필요.

## 권장 착수 순서

시간 대비 효과 기준으로 묶으면:

1. **자동 저장(1~2h) + 방향키 미세 이동(30분~1h) + z-order(1h)** — 셋 다 합쳐도 반나절이 안 되는데,
   자동 저장은 "크래시 = 전체 작업 손실"이라는 최악의 리스크를 없애고, 방향키 이동은 이번 세션에서
   반복했던 수작업 픽셀 맞추기 상당수를 대체한다. **가장 먼저 할 항목.**
2. **정렬 가이드+스냅(4~6h)** — 셋보다는 오래 걸리지만, 이번 세션 전체가 증명하듯 이 프로젝트에서
   가장 자주 겪는 마찰(여백/간격 맞추기)을 근본적으로 없애주는 항목이라 투자 대비 효과가 가장 큼.
3. **Undo/Redo(4~7h)** — 안전망 성격이라 당장 못 써도 티가 안 나지만, 없으면 실수 하나가 위젯+
   연결된 동작 코드를 통째로 날린다는 점에서 리스크가 큼.
4. 나머지(속성 패널, 다크모드, 위젯 확장 등)는 P0 네 가지가 끝난 뒤 필요에 따라 순서 조정.

**반응형 내보내기(15번)는 이 순서에서 의도적으로 제외** - 유일하게 일 단위 작업이고, 착수 전 설계
결정이 필요해서 위 네 가지를 먼저 끝내고 별도로 논의하는 게 낫다.

## 이 문서에 담지 않은 것

접근성(스크린리더/고대비 등)과 다국어(i18n)는 GUI 품질에 큰 영향을 주지만, 이 프로젝트의 사용자층
(1인 실사용 목적)을 고려할 때 우선순위가 크게 낮다고 판단해 목록에서 제외했다. 필요해지면 별도
항목으로 다시 추가할 것.
